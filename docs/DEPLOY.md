# Деплой front-new: пошаговая инструкция для новичка

Фронт живёт в репозитории **front-new** и деплоится отдельно от бэкенда. Ниже каждый шаг описан отдельно и подробно: что делать, зачем и как проверить результат.

---

## Что нужно заранее

- **Git** и **GitHub** — репозиторий front-new на GitHub.
- **Docker** — установлен локально (для проверки образа) и на VPS.
- **VPS** — сервер с IP (например 83.222.17.192), доступ по SSH.
- **Домен** — например standart82.ru, DNS указывает на IP VPS.
- **Бэкенд** — уже работает на том же домене; репо бэкенда не меняем.

**При смене домена** (например с www.new.standart82.ru на standart82.ru) шаги на сервере описаны в **[SERVER-SETUP.md](SERVER-SETUP.md)**.

---

# Часть 1. Подготовка репозитория front-new

---

## Шаг 1.1. Убедиться, что Next.js собирается в режиме standalone

**Что делаем:** проверяем, что в `next.config.ts` включён режим `output: "standalone"`. В этом режиме Next.js создаёт минимальную сборку для запуска в контейнере.

**Зачем:** без standalone в образ попадёт лишнее, и запуск в Docker будет неоптимальным.

**Действия:**

1. Откройте файл `next.config.ts` в корне репозитория front-new.
2. Убедитесь, что в объекте конфига есть строка: `output: "standalone"`.
3. В терминале в корне репозитория выполните:
   ```bash
   npm run build
   ```
4. После успешной сборки проверьте: в папке `.next/` должна появиться подпапка `standalone` с файлами (в том числе `server.js`).

**Проверка:** если `ls .next/standalone` показывает файлы — шаг выполнен верно.

**Если сборка падает:** проверьте, что установлены зависимости (`npm ci`) и нет ошибок TypeScript/ESLint.

---

## Шаг 1.2. Создать локальный .env для проверки

**Что делаем:** создаём файл `.env` в корне репозитория из примера, чтобы локально запускать приложение и образ с правильными URL бэкенда.

**Зачем:** переменные `NEXT_PUBLIC_*` задают, куда фронт ходит за данными и какой URL сайта использовать (SEO, canonical). Без .env образ будет использовать значения по умолчанию из кода.

**Действия:**

1. В корне репозитория front-new откройте терминал.
2. Скопируйте пример:
   ```bash
   cp .env.example .env
   ```
3. Откройте `.env` в редакторе. Для продакшена обычно оставляют:
   - `NEXT_PUBLIC_GRAPHQL_URL=https://standart82.ru/graphql`
   - `NEXT_PUBLIC_UPLOAD_URL=https://standart82.ru/upload/image`
   - `NEXT_PUBLIC_SITE_URL=https://standart82.ru`
4. Сохраните файл. Файл `.env` в репозиторий не коммитится (он в .gitignore).

**Проверка:** файл `.env` существует и содержит три переменные выше (или свои значения для теста).

---

## Шаг 1.3. Собрать Docker-образ локально

**Что делаем:** собираем образ фронта из Dockerfile в корне репозитория и даём ему тег для теста.

**Зачем:** убедиться, что образ собирается без ошибок и что на сервере и в CI будет тот же процесс.

**Действия:**

1. В корне репозитория front-new откройте терминал.
2. Выполните:
   ```bash
   docker build -t front-new:test .
   ```
3. Дождитесь окончания сборки (несколько минут). В конце должно быть сообщение вроде `Successfully built ...` и `Successfully tagged front-new:test`.

**Проверка:** выполните `docker images front-new` — в списке должен быть образ `front-new` с тегом `test`.

**Если сборка падает:** проверьте, что в корне есть `Dockerfile` и `package.json`. Убедитесь, что нет синтаксических ошибок в Dockerfile. При ошибке на этапе `npm run build` проверьте шаг 1.1.

---

## Шаг 1.4. Запустить контейнер с образом и проверить в браузере

**Что делаем:** запускаем контейнер из образа `front-new:test`, пробрасываем порт 3000 и передаём переменные из `.env`.

**Зачем:** убедиться, что приложение внутри контейнера стартует и отвечает на запросы.

**Действия:**

1. В корне репозитория (где есть `.env`) выполните:
   ```bash
   docker run -d -p 3000:3000 --env-file .env --name front-test front-new:test
   ```
   Флаги: `-d` — в фоне, `-p 3000:3000` — порт хоста:контейнера, `--env-file .env` — переменные окружения, `--name front-test` — имя контейнера для удобства.
2. Откройте в браузере: http://localhost:3000
3. Убедитесь, что открывается главная страница. Если в `.env` указан прод-URL бэкенда — проверьте, что данные подгружаются (каталог, программы и т.д.).
4. Остановите и удалите контейнер:
   ```bash
   docker stop front-test
   docker rm front-test
   ```

**Проверка:** сайт на http://localhost:3000 открывается и запросы к API работают (нет пустых страниц из-за недоступного бэкенда).

**Если порт 3000 занят:** используйте другой порт, например `-p 3001:3000`, и откройте http://localhost:3001.

---

## Шаг 1.5. Создать SSH-ключ для деплоя (если ещё нет)

**Что делаем:** создаём отдельный SSH-ключ для доступа с GitHub Actions на VPS.

**Зачем:** workflow будет подключаться к серверу по SSH и выполнять команды деплоя. Для этого нужен ключ; в секреты GitHub кладётся приватный ключ, на сервер — публичный.

**Действия (на своей машине):**

1. Откройте терминал.
2. Выполните (подставьте свой email):
   ```bash
   ssh-keygen -t ed25519 -C "github-deploy-front" -f ~/.ssh/github_deploy_front -N ""
   ```
   Без пароля (`-N ""`) — иначе автоматический деплой не сможет использовать ключ.
3. Публичный ключ будет в `~/.ssh/github_deploy_front.pub`, приватный — в `~/.ssh/github_deploy_front`.

**Проверка:** файлы `~/.ssh/github_deploy_front` и `~/.ssh/github_deploy_front.pub` существуют.

**Дальше:** публичный ключ нужно добавить на VPS (шаг 2.4), приватный — в секрет GitHub (шаг 1.7).

---

## Шаг 1.6. Добавить публичный SSH-ключ на VPS

**Что делаем:** добавляем содержимое файла `github_deploy_front.pub` в список разрешённых ключей пользователя на VPS, под которым будет выполняться деплой.

**Зачем:** без этого подключение по SSH с использованием этого ключа будет отклонено.

**Действия:**

1. На своей машине выведите публичный ключ:
   ```bash
   cat ~/.ssh/github_deploy_front.pub
   ```
2. Скопируйте всю строку (начинается с `ssh-ed25519`, заканчивается комментарием).
3. Подключитесь к VPS под пользователем, от имени которого будет идти деплой (например `deploy` или `root`):
   ```bash
   ssh ПОЛЬЗОВАТЕЛЬ@IP_СЕРВЕРА
   ```
4. На сервере откройте или создайте файл авторизованных ключей:
   ```bash
   mkdir -p ~/.ssh
   chmod 700 ~/.ssh
   nano ~/.ssh/authorized_keys
   ```
5. Вставьте скопированную строку ключа в новую строку. Сохраните (Ctrl+O, Enter, Ctrl+X).
6. Установите права:
   ```bash
   chmod 600 ~/.ssh/authorized_keys
   ```
7. Выйдите из SSH: `exit`.

**Проверка:** с своей машины выполните:
```bash
ssh -i ~/.ssh/github_deploy_front ПОЛЬЗОВАТЕЛЬ@IP_СЕРВЕРА
```
Должно подключиться без запроса пароля. После проверки выйдите: `exit`.

---

## Шаг 1.7. Добавить секреты в репозиторий GitHub

**Что делаем:** в настройках репозитория front-new добавляем секреты, которые workflow использует для входа на VPS и пути к папке деплоя.

**Зачем:** без этих секретов шаг «Deploy to server» в GitHub Actions не сможет подключиться к серверу и выполнить команды.

**Действия:**

1. Откройте репозиторий front-new на GitHub.
2. Перейдите: **Settings** → **Secrets and variables** → **Actions**.
3. Нажмите **New repository secret** и создайте по одному секрету:

| Имя секрета    | Значение | Как получить |
|----------------|----------|--------------|
| `DEPLOY_HOST`  | IP VPS   | Например `83.222.17.192`. |
| `DEPLOY_USER`  | Пользователь SSH | Тот же, под которым вы подключались в шаге 1.6 (например `deploy`, `root`). |
| `DEPLOY_SSH_KEY` | Приватный ключ | На своей машине: `cat ~/.ssh/github_deploy_front`. Скопируйте **весь** вывод, включая строки `-----BEGIN ...` и `-----END ...`. |
| `DEPLOY_PATH`  | Путь к корню репо front-new на VPS | Абсолютный путь, например `/root/front-new`. |
| `DEPLOY_PORT`  | (необязательно) | Порт SSH, если не 22. Например `22`. |

4. Для каждого секрета: вставьте значение в поле **Secret**, нажмите **Add secret**.

**Проверка:** в списке секретов отображаются `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_PATH`. Значения не показываются — так и должно быть.

**Важно:** в `DEPLOY_SSH_KEY` не должно быть лишних пробелов в начале/конце и не должно быть перевода строки в конце, если он дублируется. Одна строка ключа — одна строка в буфере.

# Часть 2. Подготовка сервера (VPS)

---

## Шаг 2.1. Подключиться к VPS по SSH

**Что делаем:** подключаемся к серверу под пользователем, от которого будет работать деплой.

**Зачем:** все следующие шаги части 2 выполняются на сервере в терминале.

**Действия:**

1. На своей машине откройте терминал.
2. Выполните (подставьте пользователя и IP):
   ```bash
   ssh ПОЛЬЗОВАТЕЛЬ@83.222.17.192
   ```
3. При первом подключении подтвердите отпечаток хоста (yes).
4. Введите пароль пользователя (если настроен пароль) или войдите по ключу.

**Проверка:** в приглашении терминала отображается имя пользователя и хост (например `deploy@vps`). Вы находитесь в домашней директории пользователя на сервере.

---

## Шаг 2.2. Установить Docker и Docker Compose

**Что делаем:** устанавливаем Docker и плагин Docker Compose (v2) на VPS.

**Зачем:** образ фронта запускается через Docker; без Docker команды из корня репо не выполнятся.

**Действия (для Ubuntu/Debian):**

1. Обновите пакеты:
   ```bash
   sudo apt update
   ```
2. Установите Docker и Docker Compose:
   ```bash
   sudo apt install -y docker.io docker-compose-v2
   ```
3. Включите и запустите Docker:
   ```bash
   sudo systemctl enable docker
   sudo systemctl start docker
   ```
4. Добавьте текущего пользователя в группу docker (чтобы не писать sudo перед каждой командой docker):
   ```bash
   sudo usermod -aG docker $USER
   ```
5. Выйдите из SSH и зайдите снова:
   ```bash
   exit
   ssh ПОЛЬЗОВАТЕЛЬ@83.222.17.192
   ```

**Проверка:** выполните:
```bash
docker --version
docker compose version
```
Должны вывести версии без ошибок. Затем:
```bash
docker ps
```
Должен вывести список контейнеров (пустой или с уже запущенными) без сообщения «permission denied».

---

## Шаг 2.3. Создать каталог для проекта и склонировать репозиторий

**Что делаем:** создаём каталог и клонируем в него репозиторий front-new (например в `/root/front-new`).

**Зачем:** в `DEPLOY_PATH` (корень репо) должен лежать `docker-compose.yml`; получаем его клонированием репо.

**Действия:**

1. Создайте каталог и сделайте его владельцем текущего пользователя (подставьте свой путь, если используете другой):
   ```bash
   sudo mkdir -p /opt/front-new
   sudo chown $USER:$USER /opt/front-new
   ```
2. Перейдите в каталог:
   ```bash
   cd /opt/front-new
   ```
3. Клонируйте репозиторий (подставьте свой URL репо):
   ```bash
   git clone https://github.com/YOUR_ORG/front-new.git .
   ```
   Точка в конце — клонировать содержимое репо в текущую папку `/opt/front-new`, а не в подпапку `front-new`.
4. Проверьте содержимое:
   ```bash
   ls -la
   ls docker-compose.yml .env.deploy.example
   ```
   В корне должны быть `docker-compose.yml`, `.env.deploy.example`, `Dockerfile`, `package.json` и т.д.

**Проверка:** путь к репо (например `/root/front-new`) существует и в нём есть `docker-compose.yml`. В секрете `DEPLOY_PATH` укажите этот путь (например `/root/front-new`).

---

## Шаг 2.4. Перейти в корень репо

**Что делаем:** переходим в каталог репо, где лежит `docker-compose.yml`.

**Зачем:** команды `docker compose` должны выполняться из этой папки, иначе compose не найдёт файл и конфиги.

**Действия:**

```bash
cd /root/front-new
pwd
```

**Проверка:** вывод `pwd` — путь к корню репо (например `/root/front-new`). Дальше все шаги выполняются из этой папки.

---

## Шаг 2.5. Создать файл .env для docker-compose

**Что делаем:** создаём файл `.env` в корне репо из примера и заполняем образ фронта.

**Зачем:** в `docker-compose.yml` используются переменные `FRONT_IMAGE`, `FRONT_IMAGE_TAG`. Они задаются через `.env`.

**Действия:**

1. Скопируйте пример:
   ```bash
   cp .env.deploy.example .env
   ```
2. Откройте файл:
   ```bash
   nano .env
   ```
3. Заполните (подставьте свою организацию):
   - `FRONT_IMAGE` — образ фронта без тега, например `ghcr.io/your-org/front-new`.
   - `FRONT_IMAGE_TAG` — для продакшена оставьте `latest`; при деплое из GitHub workflow подставит нужный тег.
4. Сохраните: Ctrl+O, Enter, Ctrl+X.

**Проверка:** `cat .env` выводит строки без лишних пробелов; значения без кавычек (или в кавычках, если в значении есть пробелы).

---

## Шаг 2.6. Создать файл .env.front для контейнера фронта

**Что делаем:** создаём в корне репо файл `.env.front` с переменными окружения для контейнера фронта.

**Зачем:** Next.js читает `NEXT_PUBLIC_*` при сборке и при запуске; в контейнере они задаются через env_file, чтобы фронт ходил на правильный домен и API.

**Действия:**

1. В корне репо создайте файл:
   ```bash
   nano .env.front
   ```
2. Вставьте (домен замените при необходимости):
   ```
   NEXT_PUBLIC_GRAPHQL_URL=https://standart82.ru/graphql
   NEXT_PUBLIC_UPLOAD_URL=https://standart82.ru/upload/image
   NEXT_PUBLIC_SITE_URL=https://standart82.ru
   ```
3. Сохраните: Ctrl+O, Enter, Ctrl+X.

**Проверка:** `cat .env.front` выводит три строки с URL.

---

## Шаг 2.7. .env.backend не нужен

Бэкенд запущен отдельно; в этом репо только контейнер фронта. Файл `.env.backend` не создаём.

---

## Шаг 2.8. Запустить контейнер фронта

**Что делаем:** запускаем сервис `front` из `docker-compose.yml`. Nginx и SSL — на стороне бэкенда.

**Действия:**

1. Убедитесь, что вы в корне репо:
   ```bash
   cd /root/front-new
   pwd
   ```
2. Запустите фронт:
   ```bash
   docker compose up -d
   ```
3. Проверьте статус:
   ```bash
   docker compose ps
   ```
   Контейнер `education-center-front` должен быть в состоянии `Up`.

**Проверка:** в конфиге nginx бэкенда замените upstream frontend на `server education-center-front:3000;` и выполните `docker compose exec nginx nginx -s reload` (в папке деплоя бэкенда). После этого https://standart82.ru отдаёт фронт (/) и бэкенд (/graphql, /upload).

**Если контейнер в состоянии Exit:** выполните `docker compose logs front` и исправьте ошибки (часто неверный .env.front или образ не найден).

---

## Шаг 2.9. (Опционально) Проверить, что домен указывает на сервер

**Что делаем:** убеждаемся, что домен standart82.ru (и при необходимости www.standart82.ru) в DNS указывает на IP вашего VPS.

**Зачем:** Let's Encrypt выдаёт сертификат только если по домену на порт 80 приходит запрос на ваш сервер; иначе проверка владения доменом не пройдёт.

**Действия:**

1. На своей машине выполните (или используйте любой сервис проверки DNS):
   ```bash
   dig +short standart82.ru
   dig +short www.standart82.ru
   ```
2. В ответе должен быть IP вашего VPS (83.222.17.192). Если выводится другой IP или пусто — добавьте или измените A-записи в панели управления доменом.

**Проверка:** вывод `dig` совпадает с IP VPS.

SSL и certbot уже настроены на бэкенде; отдельно получать сертификат для фронта не нужно.

# Часть 3. Как работает деплой из GitHub

---

## Шаг 3.1. Что происходит при пуше в main

**Что делаем:** понимаем цепочку действий при merge или push в ветку `main`.

**Последовательность:**

1. В репозитории front-new вы делаете merge в `main` (или push напрямую в main).
2. GitHub Actions запускает workflow из `.github/workflows/deploy.yml`.
3. Workflow:
   - делает checkout кода;
   - определяет тег образа как `latest` (для main);
   - собирает Docker-образ и пушит его в GitHub Container Registry (ghcr.io) с тегами `latest` и `sha-<commit>';
   - по SSH подключается к VPS, переходит в каталог `DEPLOY_PATH` (корень репо), выполняет `docker compose pull front` и `docker compose up -d front`.
4. На сервере контейнер `front` перезапускается с новым образом (тег `latest`). Пользователи видят обновлённый продакшен.

**Проверка:** после пуша в main откройте вкладку **Actions** в репозитории на GitHub — последний workflow run должен завершиться зелёной галочкой. На сервере в корне репо выполните `docker compose ps` и `docker compose logs front --tail 20` — контейнер front должен быть Up и с новым образом.

---

## Шаг 3.2. Что происходит при пуше в develop (или другую ветку)

**Что делаем:** понимаем, как деплоится превью по ветке.

**Последовательность:**

1. Вы пушите изменения в ветку `develop` (или другую из списка `branches` в workflow).
2. Workflow запускается так же, но тег образа будет не `latest`, а имя ветки (например `develop`; слэши в имени заменяются на дефис).
3. Образ пушится в registry с этим тегом, затем на сервере выполняется `docker compose pull front` и `docker compose up -d front`. При этом в скрипте деплоя экспортируется переменная `FRONT_IMAGE_TAG` с тегом ветки; docker compose подхватывает её, и образ фронта подтягивается с нужным тегом.
4. На сервере поднимается фронт с образом, собранным из этой ветки (превью).

**Проверка:** после пуша в develop в Actions — успешный run; на сервере `docker compose images front` показывает образ с тегом `develop` (или другим именем ветки).

# Часть 5. Возможные проблемы

- **Workflow падает на шаге Deploy:** проверьте секреты (DEPLOY_HOST, DEPLOY_USER, DEPLOY_SSH_KEY, DEPLOY_PATH). Убедитесь, что по ключу из DEPLOY_SSH_KEY можно войти на VPS (шаг 1.6). Путь DEPLOY_PATH (корень репо) должен существовать и содержать docker-compose.yml; пользователь должен иметь право выполнять `docker compose` без sudo.
- **502 Bad Gateway в браузере:** контейнер front не запущен или падает. Выполните на сервере в корне репо `docker compose ps` и `docker compose logs front`. Часто причина — неверный .env.front или образ не найден (неверный FRONT_IMAGE/FRONT_IMAGE_TAG). Убедитесь, что в nginx бэкенда upstream frontend указывает на `education-center-front:3000`.
- **SSL:** certbot и nginx — на стороне бэкенда; отдельно для фронта SSL не настраиваем.
- **Кука авторизации не сохраняется / постоянно редирект на логин:** фронт и бэкенд должны работать с одного домена (standart82.ru). Проверьте настройки CORS и куки на бэкенде (см. docs/AUTH-COOKIES-CORS.md).

После выполнения всех шагов фронт будет в корне репо front-new, собираться в контейнерах, деплоиться через GitHub Actions при пуше в main/develop. SSL и nginx — на стороне бэкенда.
